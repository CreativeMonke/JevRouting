Empirical Trade-Off Architecture and Implementation Plan for Multi-Model Agentic Systems
Production Telemetry and the Empirical Pareto Frontier
Designing a production-grade model routing architecture requires abandoning static token-price heuristics in favor of empirical task-completion telemetry. Across the late-2026 frontier model landscape, raw per-token API list prices exhibit an inverse correlation with actual task expenditure on complex software engineering workloads. Data aggregated from the Artificial Analysis Intelligence Index (v4.3.2), the Coding Agent Index (v1.5), and Slopalytics telemetry covering 77.5 million production turns demonstrates that total task cost is governed by three interacting variables: output token verbosity during extended deliberation, multi-turn retry frequency, and prompt cache hit ratios.
A foundational distortion in model selection stems from conflating per-million-token list pricing with net cost per completed task. On the Artificial Analysis Intelligence Index, GLM-5.3-Flash carries a list price of $0.15 per million input tokens, yet consumes an average of 68,700 output tokens and 18 minutes per task, resulting in an effective cost of $0.25 per task and an index score of 41.8. Similarly, DeepSeek V4.1 Flash generates approximately 88,600 output tokens per task at 209 tokens per second, completing tasks in 5 minutes at an average cost of $0.27. Conversely, OpenAI's GPT-6.1 Sol carries a list price of $2.00 per million input tokens—more than thirteen times the nominal input rate of GLM-5.3-Flash—but completes the identical benchmark at a medium compute effort level using only 8,100 output tokens. Consequently, GPT-6.1 Sol achieves a superior Intelligence Index score of 47.8 at a lower net cost of $0.21 per task, and drops to $0.13 per task (scoring 42.1) at its lowest effort setting.


A second critical phenomenon revealed by the October 2026 benchmark corpus is the non-linear degradation of cost-efficiency—and occasional capability regression—at maximum compute effort levels (max). Leaderboard rankings typically reflect max effort configurations, obscuring severe operational penalties. Within the Claude Code harness, Claude Sonnet 5.5 initializes by default at medium effort, where it achieves a Coding Agent Index score of 45.9 at $0.62 per task in 8.5 minutes. Elevating Sonnet 5.5 to high effort yields a 9.1-point jump to 55.0 while doubling cost to $1.24 per task (12.0 minutes). Pushing further to xhigh reaches 62.9 at $3.33 per task (27.0 minutes). However, engaging max effort drives the model to execute an average of 266 turns and 87.4 minutes per task, escalating cost to $14.19 per task to achieve the top leaderboard score of 68.4. Compared against GPT-6.1 Sol at xhigh inside the Codex harness—which achieves a 62.9 Coding Agent Index score in 15.5 minutes for $1.04 per task—selecting Sonnet 5.5 at max imposes a marginal cost of $13.15 per task, or $2.39 for each additional index point.
Furthermore, allocating maximum deliberation tokens can actively degrade task outcomes due to over-exploration and context pollution. When GPT-6.1 Sol is pushed from xhigh to max effort on the Coding Agent Index, its per-task cost rises by 49% (from $1.04 to $1.55), yet its empirical score regresses from 62.9 to 60.1. Within the Anthropic model family, Claude Opus 5.5 at high effort represents the optimal operating point on the Intelligence Index, achieving a score of 53.6 at $1.82 per task—capturing 93% of its max-effort score (57.6 at $5.98 per task) for 30% of the expenditure.

Real-world telemetry from T3 Code (tracked via Slopalytics across 77.5 million prompts between September 24 and October 23, 2026) contextualizes how these models behave in active engineering workflows. In production harnesses, Claude Code accounts for 71.7% of 30-day average daily turn volume (1.9 million turns/day, down 10.1 percentage points over the 30-day window), while OpenAI's Codex accounts for 28.3% (731.8K turns/day, gaining 10.1 percentage points). Across all harnesses, Claude Opus 5.5 commands 52.2% of daily turns (1.3M turns/day, +20.6 percentage points), followed by GPT-6.1 Sol at 18.1% (467.6K turns/day, +23.4 percentage points), unreported models at 12.7%, GPT-6 Astra at 6.2%, Claude Sonnet 5.5 at 3.0%, Claude Fable 5.1 at 2.8%, GPT-6 Luna at 1.5%, GPT-6 Sol at 0.8%, and Claude Haiku 5.5 at 0.7%.
Crucially, the telemetry exposes the underlying token mechanics of agentic software engineering: an average completed turn processes 2.8 million input tokens and generates 9.3K output tokens, taking 284.1 seconds at an estimated cost of $1.28 per turn, with 14.7% of turns spawning subagents and 96.5% reaching completion. Because agents repeatedly pass system instructions, tool schemas, file trees, and multi-turn execution histories on every step, 97.9% of all input tokens are served directly from prompt caches. Any routing architecture that disrupts this 97.9% cache hit ratio will experience catastrophic cost amplification, transforming cent-level turns into multi-dollar re-prefill operations.
Cross-Provider Prompt Caching Economics and State Retention Mechanics
Because production coding agents exhibit a 300:1 input-to-output token ratio (2.8M input vs. 9.3K output per turn), prompt caching is the primary economic determinant of agent infrastructure. Across major model providers in late 2026, KV-cache billing divides into two distinct architectural regimes: a pay-to-write, read-cheap regime and a free-write, best-effort or storage-billed regime.
Under the pay-to-write, read-cheap regime practiced by OpenAI (GPT-5.6 and GPT-6 series) and Anthropic, creating a cache prefix incurs a write premium over the base input token rate—typically $1.25\times$ for standard time-to-live (TTL) windows—while subsequent cache reads receive a $90\%$ to $97.5\%$ discount ($0.10\times$ down to $0.025\times$ base input). OpenAI supports both implicit (default) and explicit caching modes via prompt_cache_options.mode and prompt_cache_breakpoint (up to 4 breakpoints per request), enforcing a 1,024-token minimum and a 30-minute TTL ("30m"), alongside prompt_cache_key isolation and generation-free cache prewarming (prewarm: true). Anthropic similarly supports automatic or explicit cache_control breakpoints (up to 4 per request, requiring 512 to 4,096 minimum tokens depending on the model) with either a 5-minute TTL ($1.25\times$ write premium) or a 1-hour TTL ($2.0\times$ write premium), discounting reads by $95\%$ ($0.05\times$) on Opus 5.5 and Sonnet 5.5 and by $97.5\%$ ($0.025\times$) on Fable/Mythos 5.1.
Conversely, under the free-write regime utilized by DeepSeek and Google Gemini, writing to the cache incurs zero upfront token premium. DeepSeek's Context Caching on Disk automatically persists fixed prefix units at user inputs, model outputs, and long-input intervals for several hours to days, charging $0.02\times$ ($98\%$discount) on deepseek-flash during peak hours ($0.006/1M tokens) and halving both input and cached rates during off-peak hours ($0.15/1M input, $0.003/1M cached read). Google Gemini offers automatic implicit caching (minimum 4,096 tokens on Gemini 4 Argon and 3.8 Flash) with no write or storage fee and a $95\%$read discount on Gemini 4 Argon ($0.10/1M cached read vs. $2.00/1M input, scheduled to double on December 1, 2026 to $4.00/1M input and $0.20/1M cached read). For Gemini 3.x and 2.5 models (excluding Gemini 4 Argon), explicit caching via ai.caches.create charges no write fee but bills an hourly storage rate ($0.50/1M tokens/hour on Gemini 3.8 Flash; $4.50/1M tokens/hour on Gemini 3.1 Pro Preview).

To formalize the trade-off between staying on a warm-cache model $M_A$ versus switching to a cheaper downstream model $M_B$ during an active session, let $L_{\text{ctx}}$ denote the shared prefix length (in millions of tokens), $L_{\text{new}}$ denote the newly appended input tokens on the current turn, and $L_{\text{out}}$ denote the expected output tokens. Under a pay-to-write regime, keeping the request on model $M_A$ (where $L_{\text{ctx}}$ is already cached) incurs a single-turn cost of:
$$C_{\text{stay}}(M_A) = L_{\text{ctx}} \cdot P_{\text{read}}(M_A) + L_{\text{new}} \cdot P_{\text{write}}(M_A) + L_{\text{out}} \cdot P_{\text{out}}(M_A)$$
Conversely, routing the turn to a cold model $M_B$ requires writing the entire accumulated prefix $L_{\text{ctx}} + L_{\text{new}}$ into $M_B$'s cache (unless context pruning is applied), yielding a cold-switch cost over $k$ subsequent turns on $M_B$ of:
$$C_{\text{switch}}(M_B, k) = (L_{\text{ctx}} + L_{\text{new}}) \cdot P_{\text{write}}(M_B) + (k - 1) \cdot L_{\text{ctx}} \cdot P_{\text{read}}(M_B) + k \cdot L_{\text{out}} \cdot P_{\text{out}}(M_B) + C_{\text{router}}$$
where $C_{\text{router}}$ is the classification overhead. For a single-turn switch ($k = 1$) without context pruning from Claude Opus 5.5 ($P_{\text{read}} = \$0.20$, $P_{\text{write}} = \$5.00$, $P_{\text{out}} = \$20.00$) to GPT-6.1 Sol ($P_{\text{write}} = \$2.50$, $P_{\text{out}} = \$10.00$), switching is economically advantageous only when the output savings exceed the cold-prefix re-prefill penalty:
$$\Delta C = C_{\text{stay}}(\text{Opus}) - C_{\text{switch}}(\text{Sol}, 1) = L_{\text{ctx}} \cdot (0.20 - 2.50) + L_{\text{new}} \cdot (5.00 - 2.50) + L_{\text{out}} \cdot (20.00 - 10.00) - C_{\text{router}} > 0$$
Simplifying this inequality reveals the exact switching boundary:
$$10.00 \cdot L_{\text{out}} + 2.50 \cdot L_{\text{new}} > 2.30 \cdot L_{\text{ctx}} + C_{\text{router}}$$
If an agent turn carries an unpruned cached history of $L_{\text{ctx}} = 1.0\text{M}$ tokens and generates only $L_{\text{out}} = 0.01\text{M}$ (10K) output tokens with $L_{\text{new}} = 0.01\text{M}$ new input tokens, staying on warm Opus 5.5 costs $\$0.20 + \$0.05 + \$0.20 = \$0.45$, whereas cold-switching the full 1.01M context to GPT-6.1 Sol costs $\$2.525 + \$0.10 = \$2.625$—nearly a $6\times$ cost increase.
However, two architectural mechanisms eliminate this cold-switch penalty in production gateways. First, single-family ladder routing and switch-back retention preserve existing cache entries across tier transitions. A common misconception in router design is that switching models mid-session invalidates or evicts the prior model's KV cache. Live gateway telemetry across 4,684 real switch-backs—where a multi-turn session transitions to a cheaper tier and later returns to the higher tier—proves that a model switch is not an eviction: 97.4% of switch-backs found the original model's cache still warm under a 5-minute TTL, and 99.3% found it warm under a 1-hour TTL. Consequently, LiteLLM production benchmarks demonstrate that combining dynamic routing with prompt caching is 37.4% cheaper on real agent traces, 46.0% cheaper on DevGPT developer chats, 44% to 50% cheaper on TwinRouterBench, and 68.7% cheaper on WildChat-1M than pinning a single cached model, whereas running a router with caching disabled increases costs by roughly $4\times$.
Second, subagent context isolation (state pruning) prevents cross-provider cache thrashing. When transitioning between distinct model families—such as moving from Anthropic Opus 5.5 to OpenAI GPT-6.1 Sol or DeepSeek V4.1 Flash—replaying raw multi-turn history not only triggers a cold cache write on $L_{\text{ctx}}$ but also risks schema rejections when provider-specific blocks (such as Anthropic thinkingblocks or cache_control markers) are replayed to non-Anthropic endpoints. By isolating downstream phases into scoped subagent calls that receive only the distilled artifact (for instance, passing a 25K design specification or an 8K git diff rather than the full 500K+ conversation trace), $L_{\text{ctx}}$ is compressed by 80% to 95%, making cross-provider down-shifting immediately profitable on the very first turn.
Discriminative System One Routing via TypeSafe Jev
Every dynamic routing architecture must pay a latency and financial tax at the classification boundary. Historically, engineering teams implemented routers using small generative LLMs (such as Claude Haiku or GPT-4o-mini) prompted to emit JSON classification labels. This pattern introduces severe production bottlenecks: generative models decode tokens sequentially, add 600 to 1,900 milliseconds of time-to-first-token overhead, charge output token fees, and occasionally violate JSON schemas.
Released in September 2026 by TypeSafe AI, Jev (jev-1.13.0 and jev-1.14.0) replaces generative prompt routing with a dedicated System One discriminative model trained exclusively on synthetic data via Reinforcement Learning for Calibrated Decisions (RLCD). Named after economist William Stanley Jevons, Jev does not generate natural-language text, code, or conversational explanations. Instead, it accepts a bounded state (text, JSON object, or array of text and images up to 32K tokens per question and 64K tokens per request) alongside a dictionary of typed questions, evaluating all questions in parallel within a single forward pass to return calibrated discrete probability distributions and confidence scores.


The TypeSafe System One API (POST https://api.typesafe.ai/v1/systemone) exposes three core question primitives—alongside spatial box bounding primitives introduced in jev-1.14.0—that can be freely combined in a single request. The noul primitive evaluates a binary yes/no proposition and returns a single calibrated probability value noul $\in [0, 1]$ representing the likelihood that the statement is true. Because the returned probability directly encodes certainty—where values near $1.0$ or $0.0$ indicate high certainty and values near $0.5$ indicate maximum uncertainty—noul responses do not include a separate confidence field. The choice primitive selects a single option from a defined map of $1$ to $255$ mutually exclusive option keys and descriptions (requests exceeding 255 options automatically switch to a slower two-stage evaluation method), returning the winning option key (choice), the full normalized probability distribution across all options (probabilities), and a distribution-derived confidence score $\in [0, 1]$ computed from the average absolute deviation around the mode. Finally, the score primitive evaluates the input state against an ordered rubric array of $2$ to $10$ self-contained level descriptions, returning a continuous probability-weighted score, an indexed legend mapping each integer level to its rubric text, the discrete probabilities distribution across all levels, and an overall confidence value.
In production gateway benchmarks conducted by LiteLLM (evaluating 240 routing calls across 80 multi-turn test cases spanning four complexity tiers: SIMPLE, MEDIUM, COMPLEX, and REASONING), Jev demonstrated decisive superiority over generative LLM classification using Claude Haiku (anthropic/claude-haiku-4-5-20251001):

While Jev excels at fast, calibrated triage, an enterprise trade-off architecture must account for its structural limitations and security boundaries. Although Jev achieves 95.0% accuracy on structured 4-tier prompt routing rubrics, independent third-party evaluations on broader, multi-step general classification benchmarks (such as the 200-item DEV Community suite in September 2026) found Jev scoring 72.5%, trailing frontier generative models such as Claude Fable 5.1 (84.0%) and GPT-6 Astra (79.0%). This divergence occurs because Jev interprets instructions literally, loses accuracy on indirect multi-step reasoning, and cannot reliably count items, execute arithmetic, or compare dates. Consequently, any routing condition that depends on quantitative thresholds—such as checking whether more than three test runs failed, whether a git diff exceeds 500 lines, or whether a timestamp precedes a cutoff date—must be computed deterministically in application code and passed into Jev's state as an explicit pre-calculated field.
Furthermore, Jev's probability calibration degrades when fed bloated, irrelevant context. Rather than passing an entire 100K-token conversation history into the classifier, the router must enforce a strict context budget, passing at most the last 3 user turns within an 8,000-character window (classifier_context_window_size: 3, classifier_context_budget_chars: 8000) and excluding verbose assistant code outputs (classifier_context_include_assistant_turns: false). From a security perspective, because Jev cannot emit prose or invoke tools, it eliminates generative hallucination and direct tool-misuse vectors. However, Jev evaluates untrusted user state, making it susceptible to prompt-injection attacks that insert fake authority claims or fabricated approval strings to shift its probability output. Because Jev outputs raw numbers without textual justification, auditing misclassifications requires logging the exact state, questions dictionary, pinned model version (jev-1.13.0), and probability vector on every call, while routing low-confidence verdicts (e.g., confidence $< 0.65$ or noul $\in [0.30, 0.70]$) to deterministic fallback rules. Finally, because TypeSafe AI does not publish Jev's weights—serving it via api.typesafe.ai with dynamic rate limits of 100,000 tokens and 80 requests per second, as well as through OpenRouter, Vercel AI Gateway, and Databricks Model Serving—organizations with strict air-gapped or on-premise data residency requirements can deploy Cloudflare Clef, an Apache-2.0 open-weight model that accepts the identical System One request schema on self-hosted datacenter GPUs and requires only a URL, API key, and model name change.
Quantitative Lifecycle Modeling and Architectural Trade-Off Simulation
To quantify how model capability, prompt caching, subagent context isolation, and subscription quota offloading interact across a realistic software engineering workflow, the following simulation models a complete four-phase development ticket lifecycle. In Phase 1 (Architecture & System Design), the agent ingests 25,000 tokens of codebase structure and 3,000 tokens of ticket specifications (28,000 input tokens total) to synthesize a 3,000-token architectural specification and file-modification plan. In Phase 2 (Code Implementation & Test Generation), the agent processes the 28,000-token prior context plus 5,000 tokens of implementation instructions and test harnesses—totaling 33,000 input tokens in a monolithic thread, or 25,000 scoped tokens when isolated to the design specification and target files—and generates 6,000 tokens of production code and unit tests. In Phase 3 (Diff Review, Linting & Security Audit), the agent evaluates the implementation against security and style rubrics to generate 2,500 tokens of structured review findings; a monolithic conversation carries 37,000 input tokens (33,000 prior context plus 4,000 new diff and prompt tokens), whereas under subagent isolation, the review subagent receives only the 8,000-token git diff and specification rubric. Finally, in Phase 4 (Pull Request Synthesis & Release Notes), the agent drafts the PR description, changelog, and merge checklist (1,500 output tokens), requiring 39,000 input tokens in a monolithic thread (37,000 prior context plus 2,000 new tokens) but only 3,000 input tokens (commit log and PR template) in a scoped subagent call.
Four distinct routing architectures are evaluated against this four-phase workload using verified October 2026 API rates, incorporating a per-phase Jev routing decision overhead of approximately 1,200 tokens at $0.042/1M ($0.0000504 per call). Under Regime 1 (Monolithic Frontier Pinning on Pure Claude Opus 5.5), every phase executes on Claude Opus 5.5 within a single continuous session: Phase 1 writes 28K tokens to the 5-minute cache ($5.00/1M), while Phases 2, 3, and 4 read the accumulated prefix from cache ($0.20/1M) and pay $5.00/1M only on newly appended input tokens, with all outputs billed at $20.00/1M. Under Regime 2 (Naive Dynamic Routing with Full-Context Bouncing), Jev routes Phase 1 to Claude Opus 5.5, Phase 2 to GPT-6.1 Sol, Phase 3 to DeepSeek V4.1 Flash, and Phase 4 to GPT-6 Luna, but because the orchestrator naively forwards the entire accumulated conversation history to each new model, every phase transition suffers a 100% cold-cache penalty on the full 33K–39K token history. Under Regime 3 (Cache-Aware Dynamic Routing with Subagent Context Isolation), Jev routes each phase to its Pareto-optimal model tier while the orchestrator enforces strict subagent state boundaries: Phase 1 runs on Opus 5.5 (28K input, 3K output), Phase 2 spawns an implementation subagent on GPT-6.1 Sol (xhigh/medium) with a scoped 25K payload, Phase 3 dispatches only the 8K git diff and security rubric to DeepSeek V4.1 Flash, and Phase 4 sends only the 3K commit summary to GPT-6 Luna. Under Regime 4 (Hybrid Quota-Backed Copilot + Cache-Aware Dynamic Router), the workflow follows Regime 3 except that Phase 2 (high-volume code generation on GPT-6.1 Sol or Claude Sonnet 5.5) is routed through a LiteLLM proxy connected to an organization's existing fixed-seat GitHub Copilot Enterprise or Business subscription quota at zero marginal token cost, reserving direct pay-per-token API spend strictly for Phase 1 architectural synthesis on Opus 5.5 and fractional-cent subagent audits in Phases 3 and 4.


Inspecting the phase-by-phase mathematics in the table below reveals a crucial second-order architectural finding in Phase 2. Under Regime 1 (Pure Opus 5.5), Phase 2 reads 28,000 tokens from Opus's warm cache at $0.20/1M ($0.0056), writes 5,000 new tokens at $5.00/1M ($0.0250), and generates 6,000 output tokens at $20.00/1M ($0.1200), totaling $0.1506. Under Regime 2 (Naive Dynamic Routing), switching Phase 2 to GPT-6.1 Sol halves the output cost to $0.0600 (6,000 tokens at $10.00/1M), but because GPT-6.1 Sol has no warm cache for the session, writing the full 33,000-token context at $2.50/1M costs $0.0825—yielding a Phase 2 total of $0.1426. Thus, naive context bouncing forfeits 90% of the expected input savings on the implementation turn. Full Production Implementation Blueprint
To operationalize this trade-off architecture without relying on legacy single-harness abstractions, the production stack is organized into four modular layers: Pre-Routing State Sanitization and Parallel Jev Evaluation, LiteLLM Gateway Auto-Router and Quota Bridging, Cache-Aware Pod Discovery and Session Affinity, and Cross-Provider Effort Normalization and Spend Telemetry.
Layer 1: Pre-Routing State Sanitization and Parallel Jev Evaluation Engine
Before invoking any generative LLM, the application gateway executes a lightweight pre-processing pass that computes deterministic quantities in code (such as changed line counts, file counts, and retry counters), strips unrelated database fields or PII, and dispatches a single parallel request to TypeSafe Jev using a pinned model version (jev-1.13.0). Because Jev evaluates all questions in parallel, the gateway simultaneously queries a choice primitive for complexity tiering, a score primitive for operational risk gating, and a noulprimitive to determine whether the task can be isolated into a pruned subagent context.
TypeScript

import { choice, noul, score, TypeSafeClient } from '@typesafe-ai/sdk';

// Pin exact model version after calibrating thresholds on a labeled eval set
const jevClient = new TypeSafeClient({
  apiKey: process.env.TYPESAFE_API_KEY,
  defaultModel: 'jev-1.13.0',
});

export interface SanitizedTaskState {
  userPrompt: string;
  recentUserTurns: string[]; // Capped at 3 turns, <= 8,000 chars total
  deterministicMetrics: {
    modifiedFileCount: number;
    diffLineCount: number;
    consecutiveTestFailures: number;
    hasExplicitSpecArtifact: boolean;
  };
}

export async function evaluateRoutingDecision(state: SanitizedTaskState) {
  // Deterministic hard-override before calling Jev:
  // Jev does not count or do math reliably; handle numeric escalations in code
  if (state.deterministicMetrics.consecutiveTestFailures >= 3) {
    return {
      targetTier: 'ARCHITECTURAL_DEEP',
      effortLevel: 'high',
      isolateSubagentContext: false,
      requireHumanApproval: false,
      routingSource: 'deterministic_escalation',
    };
  }

  try {
    const response = await jevClient.systemOne({
      state,
      questions: {
        complexityTier: choice(
          'Select the optimal engineering execution tier for this task.',
          {
            ARCHITECTURAL_DEEP:
              'Multi-service system design, complex concurrency debugging, security-critical cryptography, or root-cause analysis across unknown modules.',
            IMPLEMENTATION_CORE:
              'Standard feature implementation, multi-file refactoring, writing unit or integration tests, or resolving well-scoped bugs.',
            DIFF_AUDIT:
              'Code review, static lint verification, changelog verification, or checking a git diff against a specification rubric.',
            BOILERPLATE_FAST:
              'Formatting, PR description generation, release notes, commit message drafting, or simple configuration edits.',
          }
        ),
        operationalRisk: score(
          'Rate the operational and security blast radius of executing this request.',
          [
            'Read-only analysis, documentation, or isolated unit test changes with zero production impact.',
            'Standard application code or non-destructive schema changes covered by automated test suites.',
            'Destructive database migrations, authentication/permission changes, shell execution, or billing logic.',
          ]
        ),
        canPruneContext: noul(
          'Can this task be executed using only the latest specification or git diff without full prior conversation history?',
          {
            true: 'The task is a self-contained implementation from a spec, a diff review, or PR summary.',
            false: 'The task relies on unresolved ambiguity or iterative debugging from earlier conversation turns.',
          }
        ),
      },
    });

    const tierDecision = response.answers.complexityTier;
    const riskDecision = response.answers.operationalRisk;
    const pruneDecision = response.answers.canPruneContext;

    // Confidence Gate: If Jev confidence is below 0.65, fall back to safe default tier
    const selectedTier =
      tierDecision.confidence >= 0.65 ? tierDecision.choice : 'IMPLEMENTATION_CORE';

    // Risk Gate: High-blast-radius tasks (Score >= 1.65) force high-capability review or human gate
    const requireHumanApproval =
      riskDecision.score >= 1.65 && riskDecision.confidence >= 0.60;

    return {
      targetTier: selectedTier,
      confidence: tierDecision.confidence,
      riskScore: riskDecision.score,
      // Trigger subagent context pruning only when Noul probability >= 0.75
      isolateSubagentContext:
        pruneDecision.noul >= 0.75 &&
        state.deterministicMetrics.hasExplicitSpecArtifact,
      requireHumanApproval,
      classifierModel: response.model,
      routingSource: 'jev_system_one',
    };
  } catch (error) {
    // Resilient fallback on API timeout, 422 validation error, or rate limit (80 RPS / 100k TPM)
    return {
      targetTier: 'IMPLEMENTATION_CORE',
      effortLevel: 'medium',
      isolateSubagentContext: false,
      requireHumanApproval: false,
      routingSource: 'fallback_default',
    };
  }
}

Layer 3: Cache-Aware Pod Discovery and Multi-Cluster Session Affinity
A critical failure mode in load-balanced gateways occurs when a model tier is backed by multiple cloud deployments (such as balancing Claude Opus 5.5 across direct Anthropic API keys and AWS Bedrock accounts) or multiple self-hosted vLLM GPU pods. Under naive round-robin or random-shuffle routing, each backend receives only a fraction of a conversation's turns, driving cache hit rates from approximately 95% down to near zero.
The gateway configuration above resolves this at both the cloud deployment level and the Kubernetes pod level without sacrificing the cost savings of dynamic tier down-shifting. At the cloud deployment level, session_affinity is intentionally left disabled at the top-level router so that a conversation is not permanently pinned to Claude Opus 5.5 during simpler follow-up turns. Instead, enabling the prompt_caching and deployment_affinity pre-call checks ensures that whenever the router selects the claude-opus-5-5-arch tier—including on a switch-back several turns later—LiteLLM routes the request back to the specific deployment (Anthropic direct versus AWS Bedrock) that holds that session's warm KV cache.
At the self-hosted infrastructure level, enabling kubernetes_pod_discovery: true in conjunction with a headless Kubernetes Service (clusterIP: None) allows LiteLLM to resolve individual ready vLLM pod IPs via DNS, refreshing cached pod sets every 5 seconds (KUBERNETES_POD_DISCOVERY_REFRESH_INTERVAL_SECONDS=5) and evicting idle sets after 300 seconds (KUBERNETES_POD_DISCOVERY_IDLE_EVICTION_SECONDS=300). LiteLLM extracts the session identifier from incoming request bodies or HTTP headers (such as x-litellm-session-id, x-claude-code-session-id, or Codex's session-id and thread-id) and computes a deterministic pod ranking using rendezvous hashing. Because rendezvous hashing is stateless, multiple LiteLLM proxy replicas independently select the exact same GPU pod for a session without requiring a shared Redis lookup table, and when pods scale up or down, only the minimum fraction of sessions remap while all other active sessions keep their warm vLLM prefix caches intact. If a pod fails mid-session, LiteLLM automatically retries the next pod in that session's deterministic hash ranking without permanently mutating the session's primary pod assignment.
Layer 4: Cross-Provider Effort Normalization and Governance Telemetry
When routing across Anthropic, OpenAI, Google, and DeepSeek models, parameter mismatches around extended thinking and context windows frequently trigger HTTP 400 or 422 rejections. First, the gateway normalization layer must strip legacy explicit token budgets (budget_tokens and thinking_budget), as both Anthropic and Google have deprecated raw token-budget controls in favor of unified effort levels. Crucially, on Anthropic Claude 4.7+ and all Claude 5.5 and 5.1 models, passing budget_tokens is unsupported and raises a hard API error; all requests must standardize on reasoning_effort (low, medium, high, xhigh, max).
Second, the router must clamp effort scales to match provider-specific schemas. While OpenAI (GPT-5.6, GPT-6 Astra, GPT-6.1 Sol) and Anthropic (Claude 5 series) support granular effort increments, GPT-5.6 and GPT-6 Astra map minimal to low, and DeepSeek V4 models (deepseek-v4.1-flash, deepseek-v4-pro) think by default at high effort and accept only a three-level scale (low, high, max). Because DeepSeek maps xhighdown to high, only max triggers its deepest deliberation mode. Furthermore, when routing multi-turn tool-calling loops to DeepSeek models, the orchestrator must enable Replay Reasoning—sending earlier reasoning_content blocks back in subsequent tool-call rounds—to maintain reasoning continuity.
Third, the gateway should actively manage cache breakpoints and prewarming. On OpenAI GPT-6.1 Sol and GPT-6 Luna, the orchestrator should bind prompt_cache_key to a deterministic session or repository hash to prevent cross-user cache probing and maximize server-side locality, while invoking prompt_cache_options: { mode: "explicit", prewarm: true } when loading a repository's static file tree so the cache prefix is populated prior to the first interactive turn. On Anthropic models, the gateway should inject explicit cache_control: { type: "ephemeral", ttl: "1h" } breakpoints on system prompts and tool definitions during long-running background workflows, while defaulting to "5m" TTLs for interactive turns where average turn durations are 284.1 seconds. Finally, financial telemetry pipelines must account for how LiteLLM records classifier expenditure: every Jev routing decision writes a dedicated database spend row (averaging $0.0000321 per call) and simultaneously attaches routing_decision.classifier_cost inside the completion response's routing metadata. Analytics pipelines must sum database spend rows directly rather than adding routing_decision.classifier_cost onto existing spend rows, preventing double-counting of classification overhead.
